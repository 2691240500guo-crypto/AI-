### 2.2 节点（3 类标签，78 个）

| 标签 | 优化前 | 优化后 | 示例 |
|---|---|---|---|
| `Food` 食物 | 30 | **44** | 鸡蛋、燕麦、三文鱼、橄榄油、牡蛎、**腌制食品、动物内脏、含糖饮料** |
| `Nutrient` 营养素 | 13 | **19** | 蛋白质、膳食纤维、钙、钾、**钠、嘌呤、游离糖、胆固醇、饱和脂肪** |
| `Disease` 疾病 | 14 | **15** | 高血压、2型糖尿病、骨质疏松、缺铁性贫血、肌少症、**痛风** |

> 新增的「钠 / 嘌呤 / 游离糖 / 胆固醇 / 饱和脂肪」是**风险方向**营养素，
> 配合 `加重` 关系，让图谱能表达「为什么忌口」而不只是「忌什么」。

### 2.3 关系（6 类，115 条）

| 关系 | 优化前 | 优化后 | 方向 | 语义 |
|---|---|---|---|---|
| `含有` | 30 | 45 | (Food) → (Nutrient) | 食物富含某营养素 |
| `降低风险` | 8 | 9 | (Nutrient) → (Disease) | 正向营养干预 |
| `缓解` | 7 | 7 | (Nutrient) → (Disease) | 正向营养干预 |
| `加重` | 0 | **6** | (Nutrient) → (Disease) | 风险营养素，禁忌的依据 |
| `适宜` | 0 | **33** | (Food) → (Disease) | 直接推荐（可解释、免两跳） |
| `禁忌` | 0 | **15** | (Food) → (Disease) | **直接禁忌，排菜避让的事实来源** |

关系上带 `note` 属性（如 `("钠")-[:加重 {note:"钠潴留升高血压"}]->("高血压")`），前端可视化时作为边标签展示。

### 2.4 数据来源与隔离设计

- 数据写在 `neo4j_client.py` 的 Python 常量里（`PRESET_NUTRIENTS` / `PRESET_FOODS` /
  `PRESET_DISEASES` / `PRESET_FOOD_DISEASE_RELATIONS` / `FOOD_ALIASES` / `DISEASE_ADVICE`）
- 导入使用 `MERGE`，幂等；`reset=True` 时先 `DETACH DELETE` 三类标签再重建
- **标签隔离**：只操作 `Food/Nutrient/Disease`，避免误伤同容器里其它项目的图谱（代码注释明确提到「人才库图谱」）——这是很正确的工程习惯
- **来源可追溯**：LLM 抽取的关系带 `source = "llm:<文件名>"`，与人工预置关系区分，可一键回滚

### 链路 1：图谱可视化（✅ 正常）

```

  ├─ 初始化：GET  /api/graph/stats   → 顶部显示规模提示
```

### 链路 2：智能测评 → 图谱提示（⚠️ 已接线但基本失效）

```
AssessmentPage.vue submit()
  └─ 若 form.disease_condition 非空：
       GET /api/graph/assess-hint?disease=XXX
              ↓
       Neo4jClient.search_disease(keyword)
              ↓
       Cypher：MATCH (d:Disease {name: $kw})   ← 精确匹配！
              ↓
       返回 {disease, advice, nutrients[], foods[]}
```

**实测缺陷**：`search_disease` 用的是**精确等值匹配**，而测评表单里 `disease_condition` 是**自由文本输入框**（placeholder 为「疾病描述（用于图谱关联）」）。两者的形态根本对不上。

对库内 22 种真实疾病描述逐个实测：

| 输入值 | 结果 |
|---|---|
| `骨质疏松` | ✔ 命中 |
| `高血压（稳定期）` ×4 | ✘ 未命中 |
| `2型糖尿病（稳定期）` ×4 | ✘ 未命中 |
| `2型糖尿病稳定期` ×1 | ✘ 未命中 |
| `慢性胃炎`、`脂肪肝（轻度）`、`甲状腺功能减退` | ✘ 未命中 |
| `急性脑中风，需鼻饲营养`、`胃癌术后化疗期`、`慢阻肺急性加重期` | ✘ 未命中 |
| `肺部感染住院`、`结肠肿瘤术后`、`髋部骨折卧床`、`胃部手术恢复期` | ✘ 未命中 |

**命中率：1 / 22 = 5%**

只有完全裸写疾病名（如「骨质疏松」）才能命中；只要带了「（稳定期）」「稳定期」这类限定词，或者疾病本身不在图谱的 14 个节点里，就直接返回空。

用户感知到的是：**做完测评，图谱提示卡片几乎永远不出现**。

### 链路 3：AI 问答（❌ 未接入图谱）

```
AssistantPage.vue → POST /api/assistant/chat
        ↓
assistant_service.py
  ├─ route_agents(message)：关键词命中 → 选 1~3 个 specialist + health
  ├─ run_agent_workflow()：LangGraph StateGraph 线性串联各节点
  └─ _invoke_specialist() 每个节点内：
       ├─ Milvus 向量检索（knowledge_search，top_k=5）← 唯一的检索来源
       └─ system prompt = 用户画像 JSON + 知识库片段 + 历史
```

关键事实：**`assistant_service.py` 里没有任何 Neo4j 调用**。问答的结构化知识来源只有两处：

1. 用户画像（`allergies` / `conditions` 等字段）直接塞进 system prompt
2. Milvus 向量检索返回的知识库文档片段

图谱里那些精心定义的「高血压 → 钾 → 香蕉/土豆」这类三元组，**AI 问答一个字都用不上**。

LangGraph 编排是「线性链」而非条件分支图：`route_agents()` 先用关键词选出 agent 列表，再按顺序 `START → A → B → END` 串起来，`MAX_AGENT_STEPS = 4` 防循环。设计克制、可控，但也意味着图谱无法作为「工具节点」被动态调用。

### 链路 4：饮食计划（❌ 完全未接入）

```
MealPlanPage.vue → POST /api/plans/generate {goal, days, variant}
        ↓
plan_service.py PLAN_SETS  ← 硬编码的 3 档 × 5 套菜单
        ↓
按目标热量档位选取 + variant 轮换/随机
```

`plan_service.py` 是纯静态菜谱库（低卡 / 均衡 / 高能三档），**没有任何图谱或画像参与**。这意味着：

- 用户画像里写了「海鲜过敏」，计划里照样可能出现虾仁、鲈鱼
- 用户有「高血压」，计划不会主动避开腌制/高钠食材
- 「按疾病推荐食材」这个图谱最擅长的场景，在这里完全没被使用

这是与图谱相关度最高、但目前零接入的场景——**也是答辩时最容易被追问的点**。

## 五、优化方案

### 第一档：修复命中率（半天，答辩前强烈建议）

**目标：命中率 5% → 接近 100%**

**改法 A：`search_disease` 改模糊匹配 + 多命中**

```python
def search_disease(self, keyword: str) -> List[Dict[str, Any]]:
    """支持「高血压（稳定期）」这类带限定词的输入：先用关键词反查疾病节点。"""
    kw = (keyword or "").strip()
    if not kw:
        return []
    with self.driver.session() as s:
        # 1) 疾病节点反查：双向 CONTAINS + 别名匹配
        hit = s.run(
            """
            MATCH (d:Disease)
            WHERE $kw CONTAINS d.name
               OR d.name CONTAINS $kw
               OR any(alias IN coalesce(d.aliases, []) WHERE $kw CONTAINS alias)
            RETURN d.name AS name
            ORDER BY size(d.name) DESC
            LIMIT 3
            """,
            kw=kw,
        ).data()
    return [self._disease_detail(row["name"]) for row in hit]
```

**改法 B（更稳，推荐同时做）**：测评页把「疾病描述」从自由输入改成**下拉多选**，数据源直接复用已有的 `GET /api/graph/diseases`。

```vue
<!-- AssessmentPage.vue：自由输入 → 多选，从源头消除漂移 -->
<n-select
  v-model="form.diseases"
  :options="diseaseOptions"
  multiple
  filterable
  placeholder="选择已确诊疾病（可多选，没有可留空）"
/>
```

这样既修了命中率，又让「测评→图谱」的联动在答辩时**每次都能稳定触发**。

**改法 C：给疾病节点补别名**

```python
PRESET_DISEASE_ALIASES = {
```

在 `_invoke_specialist()` 里，Milvus 检索之外再加一次图谱查询：

```python
# 1) 现有：向量检索（非结构化知识）
knowledge_hits = get_milvus().search(message, top_k=5)

# 2) 新增：图谱检索（结构化知识）——把用户画像里的疾病拿去查
graph_context = ""

    from app.utils.neo4j_client import get_neo4j

        h = hits[0]
        graph_context = (
            f"【营养知识图谱】疾病：{h['disease']}；"
            f"干预建议：{h['advice']}；"

        )

system_prompt = f"用户画像：{json.dumps(profile, ensure_ascii=False)}"
if graph_context:
    system_prompt += "\n" + graph_context
if knowledge_context:
    system_prompt += "\n" + knowledge_context
```

**答辩演示价值**：同一句「我有高血压，晚上吃什么好？」——关闭图谱开关时 AI 泛泛而谈，打开后能准确说出「限盐 <5g/d、增加钾摄入、推荐香蕉/土豆/菠菜」。这个对比比任何 PPT 都有力。

**2.2 饮食计划接入图谱做禁忌过滤**

```python
def filter_by_graph(recipes: list[dict], profile: dict) -> list[dict]:
    """用图谱 + 画像对菜单做禁忌过滤与标注。"""
    allergies = (profile.get("allergies") or "").strip()
    conditions = (profile.get("conditions") or "").strip()
    excluded, warnings = [], []
    for r in recipes:
        names = " ".join(i.get("name", "") for i in r.get("ingredients", []))
        # 过敏原排除（海鲜/虾/鱼/芒果/乳制品…）
        if allergies and allergies != "无":
            allergen_map = {"海鲜": ["虾", "鱼", "蟹", "贝", "牡蛎"], "乳糖": ["牛奶", "酸奶", "奶酪"]}
            for k, items in allergen_map.items():
                if k in allergies and any(i in names for i in items):
                    warnings.append(f"{r['name']}：含{k}，已标记过敏风险")
        # 疾病禁忌（高血压 → 高钠食材）
        if "高血压" in conditions and any(i in names for i in ["腌制", "咸菜", "腊肉"]):
            warnings.append(f"{r['name']}：高钠，建议替换")
    return warnings
```

在计划卡片上展示这些提示，就实现了「过敏/疾病 → 图谱 → 菜单」的完整闭环。

## 六、答辩建议

1. **如实说边界，再展示修复对比**——先讲清「图谱原来是展示型、RAG 是问答型、禁忌规则写在代码里」，
   再演示三档优化后的前后对比（命中率 5%→64%→100%、禁忌覆盖 6→24 项、节点 57→115）。
   这比假装全链路都通要稳得多，评委追问时也不会翻车。

2. **突出图谱的不可替代性**——纯向量检索回答「高血压吃什么」只能召回文档片段；图谱能给出确定的三元组链路
   （高血压 ←钾← 香蕉/土豆），且可解释、可溯源。这是知识图谱相对于 RAG 的核心卖点，建议做成一张对比图。

3. **最推荐的现场演示**：图谱页 → 多跳推理面板 → 选「骨质疏松」→ 显示
   「骨质疏松 ←降低风险— 钙 ——含有—— 酸奶/芝麻/豆腐」；然后在「排除食物」里填 `牛奶,酸奶`
   （模拟乳糖不耐受），点推理 —— **牛奶/酸奶从推荐里消失并被单独列出原因**。
   这个动作 10 秒钟，把「图谱能推理、能结合个性化约束」讲得比任何 PPT 都清楚。

4. **准备好被问的四个问题**：
   - 「图谱多少节点？」→ **115 节点 / 164 关系**（食物 78 / 营养素 22 / 疾病 15），并说明可继续用 LLM 扩谱
   - 「为什么用 Neo4j 而不是关系库？」→ 营养知识本质是多跳关联查询，Cypher 两跳/三跳远比 SQL JOIN 直观；
     本轮的禁忌避让正是「食物→营养素→疾病」两跳推断的产物
   - 「怎么保证知识准确？」→ 预置知识来自营养学共识；LLM 抽取的三元组**必须带文档原文证据句**、
     打 `source` 标记可溯源可回滚，且只作**观察参考**，不做诊断结论（与免责声明口径一致）
   - 「规则要改怎么办？」→ 不用改代码：往图谱加一条 `(食物)-[:禁忌]->(疾病)` 关系即生效（服务启动自动增量补齐）

### 7.3 关键设计决策

**1) 为什么把禁忌规则从代码搬到图谱？**

原实现是 `DISEASE_AVOID_KEYWORDS = {"高血压": ["腌制","咸菜","腊肉",...]}`——关键词硬编码。
问题不只是覆盖少，而是**它无法表达"为什么"**，也无法让非开发者维护。

搬进图谱后：
- 规则带 `note` 说明依据（如 `钠 --加重--> 高血压 {note:"钠潴留升高血压"}`）
- 加一条边即刻生效，无需改代码/发版（服务启动自动增量补齐）
- 可被其他链路复用（问答、图谱页推理面板、未来的营养师后台）

代码里的词表**没有删除**，而是降级为「图谱不可用时的离线兜底」——保证 Neo4j 挂掉也能出计划。

**2) 为什么不用纯 LLM 替代图谱？**

LLM 生成约束不可复现、不可审计。图谱给出的结论是**确定且可溯源**的：
`(钠)-[:加重 {note}]->(高血压)` 这条边，任何时候查都是同一结果，且能指出依据。
LLM 在本方案里的角色是**建谱助手**（把文档转成三元组），而不是在线决策者——
决策仍由图谱的确定关系完成。这是「LLM 负责广度、图谱负责确定性」的分工。

**3) 两跳推断：让扩谱立刻产生业务价值**

单纯往图谱塞节点不会改变任何业务行为。真正起作用的是这条推断：

```
(食物)-[:含有]->(营养素)-[降低风险|缓解|加重]->(疾病)
        ↓ 自动推断
(食物) 对 (疾病) 是「适宜」还是「禁忌」
```

例：LLM 从文档抽到「酱油-含有-钠」，而图谱里已有「钠-加重-高血压」，
系统立刻得出「酱油对高血压禁忌」——**这是原先代码词表完全没有的能力**。
所以扩谱不是"节点数好看"，而是直接增加了 300% 的禁忌覆盖。

**4) 泛化词过滤**

LLM 会把「蔬菜」「豆类」「全谷物」这类统称也抽成食物。这些词作为 `Food` 节点
在排菜匹配时会误命中所有含该词的菜，且无法给出具体替代建议，因此在写库前过滤（本次过滤 6 条）。

### 7.4 图谱维护方式的变化

| | 优化前 | 优化后 |
|---|---|---|
| 新增知识 | 改 Python 常量 → 重启服务（且启动时如果图谱非空会直接跳过导入） | 写一条三元组 → 重启自动**增量补齐**（MERGE，幂等） |
| 部署新图谱 | 需 `reset=True` 清空重建（有丢数据风险） | 增量补齐，已有人工关系不受影响 |
| 批量扩谱 | 无手段 | `build_graph_from_llm.py`，带 `--dry` / `--from-json` / `--clean-llm` |
| 回滚 | 只能整表重建 | 按 `source` 标记精准删除 LLM 抽取的关系 |

扩谱脚本用法（在 `backend` 目录）：

```bash
./venv/Scripts/python.exe scripts/build_graph_from_llm.py --dry         # 抽取 + 预览，不写库
./venv/Scripts/python.exe scripts/build_graph_from_llm.py --from-json   # 审查后写入
./venv/Scripts/python.exe scripts/build_graph_from_llm.py --clean-llm   # 回滚 LLM 抽取的关系
```

### 7.6 已知边界（如实说明）

| 边界 | 说明 | 后续 |
|---|---|---|
| 疾病覆盖面 | 15 个疾病节点，仍覆盖不了「慢性胃炎」「甲状腺功能减退」等 | 扩谱脚本可继续从文档抽取；或接入公开营养知识库 |
| 两跳推断的严格性 | 「食物-含有-营养素-加重-疾病」推断出的禁忌未区分剂量（如适量酱油并非绝对禁止） | 建议后续给关系加 `severity` / `threshold` 属性 |
| LLM 抽取质量 | 抽取结果基于文档原文且带证据句，但仍建议人工抽检 | 已在 `data/graph_llm_extraction.json` 留档 |
| 过敏原仍在代码里 | 过敏是"具体食材写法"级事实（「鲈鱼」「基围虾」都算海鲜），枚举成图谱边反而臃肿 | 保持词表，与图谱互补 |
| 医学口径 | 所有建议均限定为「观察参考」，不构成诊断或治疗建议 | 与免责声明口径一致 |
