3.2 路由规则：一句话怎么变成 Agent 编排

路由发生在进图之前（route_agents()，assistant_service.py 第 111 行），按固定顺序扫描关键词表：

Agent命中关键词（ROUTE_KEYWORDS）角色定位
营养师 Agent
nutrition		吃 / 饮食 / 营养 / 热量 / 食谱 / 蛋白 / 维生素 / 餐 / 减脂 / 减重 / 增肌饮食与营养专科
运动 Agent
exercise		运动 / 步数 / 跑步 / 健身 / 心率 / 锻炼 / 训练运动处方专科
睡眠 Agent
sleep		睡眠 / 睡不着 / 失眠 / 深睡 / 作息 / 熬夜睡眠专科
健康管理 Agent
health		不设关键词——三种情况被启用（见下）兜底 + 跨域汇总
plan 的三种形态：
单域 只命中一个领域 → plan = [该专科]（如只问"怎么减脂" → [nutrition]），健康管理 Agent 不参与
多域 命中 ≥2 个领域 → plan = [专科按固定顺序] + 追加 health 收尾汇总（如"减脂又失眠" → [nutrition, sleep, health]）
零命中兜底 一个关键词都没中 → plan = [health]，由健康管理 Agent 独立作答

3.3 每个 Agent 节点内部：统一的 RAG 融合流水线

四种 Agent 的 node 函数是同一个模板（run_node → _invoke_specialist），只有角色人设和提示词不同：

① Milvus 向量检索 → 拿知识库 top5 片段，拼成「知识库参考」system 消息（模糊知识，仅供参考）
② Neo4j 图谱推理 → 用画像疾病 + 本轮消息做别名对齐（_match_diseases），再跑 reason_path 多跳推理：疾病 → 营养素 → 食物，产出宜吃/忌口/过敏剔除，拼成「结构化结论」system 消息，与知识库片段冲突时图谱优先
③ 个性化上下文 → 用户画像（目标/过敏/疾病）+ 长期记忆（allergy/condition/goal/preference 四类）+ 近 12 条会话历史
④ 一次 LLM 调用 → system（角色人设 + ①②③ 内容 + 前序交接）+ user（本轮消息）→ 输出专科回答，附 tool_calls 与 sources 供前端展示

关系机制说明（源码依据）
专科 → 专科顺序 add_edge 直线串联，无并行、无循环；StateGraph 共享 AgentRunState，每个 node 把自己的输出追加进 agent_outputs
前序 → 后序handoff 交接：后一个 Agent 的 system prompt 里拼入「前序 Agent 交接：营养师 Agent：……」（第 287-331 行），保证后序不重复劳动、结论连贯
专科 → 健康管理多域问题时 health 排最后，读全部前序输出做跨域汇总收口（例如同时回应减脂与失眠的相互作用）；单域问题时 health 完全不出现
健康管理 ↔ 兜底零命中时 health 单独成图作答，兼具「通用健康顾问」角色
全链 → 审计无论几个 Agent，结束后 persist_agent_run() 把 plan、每步输出、tool_calls、sources 落 assistant_agent_runs/steps 两张表，前端可逐步回放

3.5 State 字段与防失控设计

AgentRunState 字段作用
message本轮用户消息（全程不变）
profile用户画像（目标/过敏/疾病/偏好），注入每个 Agent
history近 12 条会话历史
agent_plan路由产出的执行计划（进图前已定，图内不改动）
agent_outputs累积输出列表，即 handoff 载体，也是最终 agent_trace
step_count步数计数（上限 MAX_AGENT_STEPS=4，plan 进图前截断）
为什么说是「有界」状态机： 没有使用 add_conditional_edges 的图内动态分支，而是「先规划后执行」——路由、截断都在进图前完成，图内只有一条直线。好处：① Agent 数量有硬上限（4），LLM 调用次数可预估（≤4 次）；② 不会出现 Agent 互相踢皮球的死循环；③ 执行路径完全可预测、可审计、可回放。代价：牺牲了图内动态决策的灵活性——这是面向答辩可讲的设计取舍。
