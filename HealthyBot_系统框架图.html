分层职责与关键约定

层职责关键约定 / 易踩坑
① 展示层页面渲染、请求封装、图表与主题
14 个页面组件		颜色只用 CSS 变量（var(--ink/--card/--primary)），硬编码 #fff 会让深色模式发白
② 接入层启动钩子（建表 + 图谱幂等灌入）、JWT 校验、健康数据授权闸门、统一响应授权接口是 PUT /api/privacy/consent（不是 POST）；未授权时业务接口返回 428 属设计而非 bug
③ 业务路由层9 个路由模块，仅做参数校验与编排调用，业务逻辑下沉 services改数据库结构走 ORM 模型 + init_db() 自动建表，项目无独立 SQL 文件
④ AI 编排层LangGraph 有界状态机、RAG 双源融合、规则引擎打分、多模态解析「先规划后执行」：路由在进图前完成，图内一条直线，最多 4 步；图谱结论与知识库片段冲突时图谱优先
⑤ 模型服务层云端六模型 + 本地 YOLO，全部经单点客户端调用LLM 单一出口 llm_client.py，各调用点都有本地兜底（模板/词表/规则），保证不白屏
⑥ 数据层MySQL 业务数据、MinIO 文件、Milvus 向量、Neo4j 图谱、Redis 缓存向量库与图谱互不写入，只在 prompt 层融合；图谱数据人工预置 + 幂等 MERGE，加一条边即刻生效

一句话读懂这张图

请求从左上角进来，沿着六层**单向向下**：前端 → 接入层校验（JWT + 授权）→ 业务路由 → AI 编排（LangGraph + RAG + 规则引擎）→ 模型服务（云端 LLM / 本地 YOLO）→ 数据层五种存储。
反向只有一条路：结果沿原路回传，同时把「谁答的、查了什么」写进 MySQL 留痕表。
架构关键词：分层单向依赖、AI 能力单点封装、双知识源 prompt 层融合、每个 LLM 调用点都有本地兜底。
